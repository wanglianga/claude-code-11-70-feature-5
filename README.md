# 化工园区监测写入与恢复控制台

面向化工园区环保值班的监测数据平台：数十个网关上报废水、废气、储罐液位与雨污切换阀门读数；暴雨、设备自检、断网恢复会让数小时补传读数与实时超标读数同时抵达。平台保证：

- **高风险超标 15 分钟内可见**：实时通道优先处理高风险分区，告警只消费已确认的高风险超标结论；
- **每条原始读数可溯源**：中心持久接收日志记录来源（网关/会话/来源序列/载荷指纹）与接收顺序（日志 id 即全中心接收顺序），监管取证期内不抽样删除；
- **恢复可核对**：恢复编排器按分区游标回补积压，运行台展示缺口、延迟与证据链。

技术栈：Vue 3 + Element Plus（前端）、FastAPI（后端）、PostgreSQL（持久化）。

## 架构选择：中心持久接收日志

原始读数保全的两种可行架构：

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 网关本地加密分段日志，恢复后带清单上传 | 中心写入压力低 | 断电后分段找回困难；全园区积压视图延后 |
| **中心持久接收日志 + 异步校验入库（本平台采用）** | 到达即统一仲裁优先级；接收顺序全局可查；取证链完整 | 中心需预留更多磁盘与写入带宽 |

平台选择**中心持久接收日志**，并将日志保留期与监管取证期绑定：低风险趋势即使延后计算，也不从日志中抽样删除。为缓解中心写入压力，平台内置背压机制：数据库写入延迟跨过高风险阈值时，调度器暂停低风险衍生计算并为高风险分区保留写入额度。

## 组件与数据流

```
网关 ──> 接入网关(会话/来源序列/载荷指纹/接收时间)
      ──> 持久接收日志(每条到达立即落库, id=接收顺序)
      ──> 批次调度器(分区积压水位 + 策略版本, 实时通道)
      ──> 质量服务(范围/时序/设备状态 三项检查 -> 结论)
      ──> 告警服务(只消费 已确认+高风险+超标 结论)
恢复编排器(按分区游标回补 补传/积压, 恢复批次)
运行台(缺口、延迟、证据链、策略台账、恢复游标)
```

关键规则实现：

1. **重传只确认一次**：同一网关会话内 `来源序列 + 载荷指纹` 相同的再次到达记为 `duplicate`，不重复确认；
2. **冲突并列不覆盖**：同会话同序列但载荷不同的后到值记为 `conflict`，与原读数并列存证（`reading_conflicts`），禁止覆盖已确认读数；
3. **策略版本固化**：批次创建时固化策略版本；批次处理期间策略升级，已生成批次仍引用创建时版本，新批次才走新优先级，恢复顺序不被追溯改写；
4. **写入背压**：写入延迟连续超阈值 → 调度器降级：实时通道只服务高风险分区、暂停低风险衍生计算（滚动均值）、恢复编排器自动回补暂停；连续恢复后自动退出降级并回补积压；
5. **校准/维护待核**：读数抵达时设备处于校准或维护状态，质量服务保留来源并给出 `pending_review`（未确认）结论，告警服务不把它当正式超标；
6. **补传分流**：读数时间早于当前 10 分钟（可配）的确认读数不占用实时通道，由恢复编排器按分区游标批量回补。

## 容量决策复盘（本次新增）

监管复盘某次暴雨告警时，需要判断临界排口的写入等待来自**真实容量耗尽**、**低风险任务未及时让位**，还是**策略版本切换后的调度缺陷**。仅靠当下日志无法还原“当时哪一批读数、哪个队列水位和哪版优先级共同决定了这次延迟”，因此新增容量决策复盘服务：

```
接收/批次生成/策略生效/批次完成 ──> 事件台账(不可变, event_seq=预登记序号)
                                    │
                           顺序规范器(同刻按 event_seq 裁定, 不按写入先后)
                                    │
检查点(当时队列水位+调度游标) ──> 回放引擎(从告警/区间重建 每一步可选批次 与 实际选择)
                                    │
                           反事实比较器(只读: 若低风险让位 / 若沿用上一策略)
                                    │
                           证据视图(结论 -> 读数/策略/处理事实) + 复盘版本(只追加)
```

对应需求的关键实现：

1. **事件顺序规范器**：接收、批次生成、策略切换、批次完成全部登记为不可变 `decision_events`，每事件带生效时刻 `effective_ts` 与**登记时派发**的 `event_seq`；同一生效时刻**一律按 `event_seq` 裁定先后**，绝不依赖数据库写入先后。策略切换与批次完成同刻时，复现给出的裁定顺序与写入顺序可不同（页面与验收脚本均核对）。
2. **状态保全器**：`queue_checkpoints` 保存某时刻各分区的积压/在途、确认/入批/处理游标与调度游标，作为区间重放起点。
3. **回放引擎**：从指定告警、读数或延迟区间重建决策时间线，逐步列出**可选批次（权重/积压）**与**实际选择**及评分说明。
4. **反事实比较器**：在内存中计算“若低风险任务未占用通道”和“若沿用上一策略”的等待差异，**不写回生产台账**；缺少当时水位或事件链断裂时只返回 `insufficient`，并明确标注“所列当前状态仅供说明，并非当时答案”。
5. **补传晚到**：晚到事件落入已复盘区间时生成**新的复盘版本 + 差异说明**，`review_runs` 只追加、不原地改写，旧版本内容哈希保持不变。
6. **证据视图**：把结论连回具体读数、质量结论、批次、策略版本与每次调度决策，支持从读数下钻原始证据链。
7. **台账保留模式取舍**（据可接受的复盘响应时间、峰值事件量与监管保留期选择，复盘页与接口给出建议与理由）：
   - `journal`：保存每一次队列比较与评分明细，查询时可直接解释决定，但持续写入量很大；
   - `checkpoint`（默认）：周期检查点 + 不可变事件序列，日常成本低，长区间复盘需按事件重放计算。
   复盘结果中均说明**重建精度**（`event_grade` / `checkpoint_grade` / `insufficient`）与成本边界。

复盘模拟序列在**隔离通道**（`lane=scenario:*`）构建，不参与真实调度、不写入生产策略台账、不出现在运行台分区完整性口径；三条必选序列为 **容量耗尽 / 低风险阻塞 / 策略切换竞争**，另有 **证据不足保护** 序列用于演示事件链断裂时只给证据不足。

## 目录结构

```
backend/            FastAPI 后端（app/ 下 models/services/routers/main）
  app/services/decision_ledger.py   事件台账/顺序规范器/检查点/成本策略
  app/services/review.py            回放引擎/反事实/复盘版本
  app/services/review_scenarios.py  容量耗尽/低风险/策略切换竞争/证据不足 模拟序列
  Dockerfile
frontend/           Vue 3 + Vite + Element Plus 前端（含 Review.vue 复盘页）
  Dockerfile  nginx.conf
scripts/verify.py          基线验收脚本（7 组场景端到端核对）
scripts/verify_review.py   复盘验收脚本（判定/顺序/版本/证据不足/隔离）
docker-compose.yml  一键启动（db + backend + frontend）
```

## 本地启动

前置：PostgreSQL 已运行（开发容器内置 `ccdev/ccdev@127.0.0.1:5432/ccdev`）；Python 3.12、Node 22。

```bash
# 1. 后端（首次会自动建表并写入种子数据；迭代升级时 ensure_schema 幂等补列）
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
cd backend && ../.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 2. 前端（二选一）
#   a. 生产模式：构建后由后端直接托管，访问 http://127.0.0.1:8000
cd frontend && npm install && npm run build
#   b. 开发模式：Vite 热更新，访问 http://127.0.0.1:5173（已配置 /api 代理）
cd frontend && npm run dev
```

启动后到「容量决策复盘」页：点击四个模拟序列的「构建」（或调用 `POST /api/review/scenarios/{capacity|low_risk|policy_race|insufficient}/build`），即可查看决策时间线、反事实差异、证据下钻；点「补传晚到 → 新版本」演示版本化。

## 验证方式

### 自动验收（推荐）

后端运行中执行：

```bash
.venv/bin/python scripts/verify.py --base http://127.0.0.1:8000
```

脚本模拟四类场景并核对一致性，全部通过时输出 `ALL CHECKS PASSED`：

1. **实时流**：注入含高风险超标的实时读数 → 核对告警产生且 接收→告警 延迟 < 15 分钟；
2. **冲突重传**：同会话同序列先发正常值、同指纹重传、再发不同载荷 → 核对 `confirmed/duplicate/conflict` 三态、已确认读数未被覆盖、冲突证据并列；
3. **补传流**：模拟断网恢复后 1 小时缓存读数集中上传 → 核对恢复编排器产生按分区游标的回补运行、覆盖全部分区；
4. **策略升级**：发布新策略版本 → 核对旧批次仍引用 v1、新批次引用 v2（策略台账）；
5. **设备校准**：设备置为校准中后注入超标读数 → 核对结论为 `pending_review` 且未确认、未产生告警；
6. **持续写入变慢**：开启慢写入（每次写注入 1.2s 延迟）→ 核对调度器降级、低风险衍生计算暂停、高风险分区保留写入额度（超标仍告警）、低风险分区积压水位上升；关闭慢写入 → 核对调度器恢复、回补后**最终分区完整性一致**（各分区 已确认=已入批=已处理）；
7. **证据链抽查**：核对高风险读数的 日志/会话/设备/批次/结论/告警 链路完整。

### 复盘验收

后端运行中执行：

```bash
.venv/bin/python scripts/verify_review.py --base http://127.0.0.1:8000
```

脚本核对（全部通过时输出 `ALL REVIEW CHECKS PASSED`）：

1. **台账模式/成本边界**：默认 `checkpoint`；严格响应+高事件量建议 `journal`，常规响应+长保留期建议 `checkpoint`；
2. **三条序列判定**：容量耗尽 → `capacity_exhausted` 且记录当时积压水位；低风险阻塞 → `low_risk_blocked` 且“低风险让位”使等待缩短；策略切换竞争 → `policy_switch_race` 且“沿用上一策略”有非零差异；
3. **顺序规范器**：同刻事件的数据库写入顺序与预登记序号顺序不同，裁定以 `event_seq` 升序、策略生效先于批次完成；
4. **状态保全**：复盘锚定区间起点检查点，检查点含分区水位与游标；
5. **补传晚到**：生成新版本、旧版本内容哈希不变、新版本带差异说明并指向被替代版本；
6. **证据不足保护**：事件链断裂时只给 `insufficient`，并标注当前状态非历史答案；
7. **台账隔离与生产复盘**：模拟数据不进入分区完整性口径；可从生产告警/区间发起复盘。

### 页面手动验证

登录后可在控制台操作：

- **运行台**：接收/确认/重传/冲突计数、写入延迟曲线与降级状态、分区积压水位与游标、告警延迟；
- **场景模拟**：一键注入 实时流/补传流/冲突重传，开关慢写入；
- **接收日志**：按会话/网关/状态过滤，id 即接收顺序；
- **质量结论**：范围/时序/设备状态三项检查结果；
- **告警**：高风险超标告警与延迟，支持确认；
- **设备目录**：维护点位阈值与运行状态（正常/校准中/维护中）；
- **策略台账**：发布新版本，查看各版本引用的批次数；
- **恢复编排**：分区游标、回补运行记录，支持手动触发回补；
- **证据链**：输入接收日志 id 查看完整溯源链；
- **容量决策复盘**：台账模式与成本边界建议；一键构建 容量耗尽/低风险阻塞/策略切换竞争/证据不足 模拟序列；决策时间线（可选批次评分 vs 实际选择）、同刻顺序裁定对照、反事实等待差异、证据下钻（读数→原始证据链）、复盘版本历史与差异说明；生产台账按告警或延迟区间复盘。

## 验证结论（实际执行记录）

在本工作区以预装 PostgreSQL 18.1 + Python 3.12.10 + Node 22.14.0 实际执行：

- `scripts/verify.py` 全部 **24 项检查通过**（输出 `ALL CHECKS PASSED`），覆盖上述 7 组场景；
- `scripts/verify_review.py` 全部 **27 项检查通过**（输出 `ALL REVIEW CHECKS PASSED`），覆盖复盘判定、顺序规范器、检查点、补传晚到版本化、证据不足保护、台账隔离与生产告警复盘；
- 实测复盘结论：容量耗尽（当时积压 6、在途 2、2 个批次竞争单通道）、低风险阻塞（低风险让位后目标等待缩短 37.5s）、策略切换竞争（策略生效与批次完成同刻，写入顺序为“完成→策略”，裁定顺序为“策略→完成”；沿用上一策略等待缩短约 3.3s）；
- 高风险超标 接收→告警 实测延迟约 0.2–0.8 秒（目标 15 分钟）；
- 降级场景实测：慢写入开启后调度器进入降级（`degraded=true, low_risk_paused=true`），高风险超标读数在降级期间仍告警（延迟约 0.2 秒），P-LOW-1 出现积压水位；关闭慢写入后调度器恢复，回补后全部分区完整性一致；
- 前端已实际构建（`npm run build`）并由后端托管验证可访问（`GET /`、`GET /review` 与 SPA 回退均 200）。

> Docker 镜像构建在本容器内无 Docker 守护进程未实际执行；Compose 配置按标准镜像（python:3.12-slim、node:22-alpine、nginx:alpine、postgres:16-alpine）编写，本地启动路径已如上实测。
